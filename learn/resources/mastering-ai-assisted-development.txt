Claude Code Hooks: Complete Guide
What are hooks? And why hooks matter
PreToolUse:
PostToolUse:
Safety: Prevent destructive commands (rm -rf, git push --force, credential exposure).
Quality: Auto-lint, format, test before code lands in your repo
Compliance: Log all code changes for audit trails.
Consistency: Enforce repo conventions automatically.
PreToolUse Hooks: Gatekeeper and confirmation
Common PreToolUse patterns:
1. Reject dangerous bash patterns:
if (toolName === "bash" && command.includes("rm -rf")) {
  return {
    status: "blocked",
    reason: "Destructive commands not allowed"
  };
}
2. Require approval for sensitive operations:
if (toolName === "bash" && command.includes("git push")) {
  return {
    status: "requires_approval",
    prompt: "This will push to remote. Approve?"
  };
}
3. Transform/sanitize commands:
if (toolName === "file_write" && path.includes(".env")) {
  return {
    status: "transform",
    newCommand: "Write to .env.example instead",
    newParams: { path: path.replace(".env", ".env.example") }
  };
}
PostToolUse Hooks: Quality gates and cleanup
Common PostToolUse patterns:
1. Auto-lint generated JavaScript/TypeScript:
if (toolName === "file_write" && filename.endsWith(".ts")) {
  const lintResult = await exec("eslint --fix " + filename);
  return {
    status: "success",
    message: "File written and linted: " + lintResult.output
  };
}
2. Run tests on modified files:
if (toolName === "file_write" && filename.includes("__tests__")) {
  const testResult = await exec("npm test -- " + filename);
  if (!testResult.success) {
    return { status: "warning", message: "Tests failed" };
  }
  return { status: "success" };
}
3. Format code with prettier:
if (toolName === "file_write" && /\.(js|ts|jsx|tsx|json)$/.test(filename)) {
  await exec("prettier --write " + filename);
  return { status: "success", message: "Code formatted" };
}
4. Prevent credential exposure:
if (toolName === "bash" && result.stdout.match(/password|token|secret|key=/i)) {
  return {
    status: "blocked",
    reason: "Output contains sensitive data"
  };
}
Hook configuration: .claude/hooks.json
{
  "preToolUse": [
    {
      "name": "block_dangerous_bash",
      "toolName": "bash",
      "rules": [
        { "pattern": "rm -rf", "action": "block" },
        { "pattern": "git push --force", "action": "require_approval" }
      ]
    }
  ],
  "postToolUse": [
    {
      "name": "auto_lint_ts",
      "toolName": "file_write",
      "filePattern": ".*\\.ts",
      "commands": [
        "eslint --fix {filepath}",
        "prettier --write {filepath}"
      ]
    }
  ]
}
Configuration options:
name: unique identifier for the hook
toolName: which tool this hook applies to (bash, file_write, git, etc.)
rules: conditions and actions (block, require_approval, transform, log)
commands: Shell commands to run (for PostToolUse)
filePattern: Regex to match files (for PostToolUse)

Debugging hooks: Troubleshooting common issues
Hook not running?
Check .claude/hooks.json exists in project root.
Verify JSON syntax (use a linter).
Ensure toolName matches exactly (case-sensitive).
Check filePattern regex with a regex tester.
Hook blocking too much?
Tighten your regex patterns.
Use filePattern to scope to specific files.
Switch from block to require_approval if the pattern is legitimate but sensitive.
Commands not executing in PostToolUse?
Test the command manually in bash (syntax may be wrong).
Use absolute paths for executables.
Ensure {filepath} is being replaced with the actual filename.
Check command timeout settings if operations are slow.
Security hooks: Preventing data leaks
Best practices for security-focused hooks:
1. Block credential patterns in output:
{
  "postToolUse": [{
    "name": "block_credential_output",
    "toolName": "bash",
    "rules": [
      {
        "outputPattern": "password|token|secret|api_key",
        "action": "block",
        "message": "Output contains sensitive data"
      }
    ]
  }]
}
2. Prevent writing to shared locations:
{
  "preToolUse": [{
    "name": "isolate_sensitive_files",
    "toolName": "file_write",
    "rules": [
      {
        "path": "/tmp|/var/log|/etc/",
        "action": "block",
        "message": "Cannot write to system directories"
      }
    ]
  }]
}
3. Audit sensitive bash commands:
{
  "preToolUse": [{
    "name": "audit_sensitive_ops",
    "toolName": "bash",
    "rules": [
      {
        "pattern": "curl.*Authorization|wget.*auth",
        "action": "require_approval",
        "message": "HTTP request with credentials"
      }
    ]
  }]
}

Debug: Check JSON syntax, regex patterns, tool names, and command paths.
Security: Prevent credential exposure, isolate system directories, audit sensitive operations.

When to Use Agents vs. Chat: Decision Framework
Summary
Decision framework based on task complexity, file count, iteration depth, cost, and risk tolerance.
The fundamental difference
Chat is reactive: you ask, AI responds, one exchange at a time. An agent is autonomous: it plans, executes, observes results, and iterates — operating in a loop without your intervention.
The Plan-Act-Observe-Adjust loop
Agents operate in a cycle:
Plan — Break the task into steps.
Execute — Write code, create files, run commands.
Observe — Read command output and test results.
Iterate — Fix problems based on observations.
Verify — Run tests to confirm correctness.
When to use chat
Quick questions about code or concepts
Explaining an error message or stack trace
Small, single-file edits
Code review of specific functions
Learning and exploration
When to use agents
Multi-file feature implementation
Codebase-wide refactoring
Test suite generation
Bug investigation and fixing
Framework or library migrations
Any task with multiple steps that requires verification
Decision matrix

Agent types in 2026
Agents now come in multiple flavors:
Local agents: interactive, run in your editor (Cursor Agent, Copilot local)
Background agents: CLI-based, run in isolated Git worktrees
Cloud agents: run on remote infrastructure, produce PRs (Copilot coding agent)
Third-party agents: From providers like Anthropic (Claude Code) and OpenAI
You can hand off between agent types — start planning locally, then hand off to a cloud agent for implementation.
The test foundation
Agents work dramatically better when your project has tests. Tests are guardrails — the agent can run them after each change to verify correctness. Without tests, the agent may claim “done” when things are actually broken.
If you take one thing from this: invest in tests. Tests are the foundation that makes agents reliable.

MCP: The Future of AI Tool Integration
Summary
Architecture details, security model, ecosystem roadmap, and why MCP is becoming the standard.
What is MCP?
Model Context Protocol (MCP) is an open standard for connecting AI tools to external systems. Think of it as “USB for AI” — a standardized way to plug different data sources and tools into any MCP-compatible AI assistant.
The problem MCP solves
Before MCP, each AI tool had proprietary integrations. Each tool had its own integrations — nothing was interoperable. MCP standardizes the protocol so any AI tool can talk to any external service.
Architecture
Three components
MCP client: your AI tool (VS Code + Copilot/Cline, Claude Code, Cursor) that wants external data
MCP server: a lightweight adapter that translates between MCP protocol and the external service’s API
External service: the actual tool or database you’re connecting to (GitHub, Postgres, Figma)
The MCP server runs on your machine, so credentials stay local. Your AI tool talks to the MCP server, and the MCP server talks to the external service.
Three key benefits
1. AI goes from guessing to knowing
Without MCP, asking “what are the open issues?” requires guessing. With GitHub MCP, the AI queries actual issues in real time.
2. One integration, many tools
An MCP server for GitHub works with VS Code, Claude Code, Cursor, and any MCP-compatible tool. Build once, use everywhere.
3. Live data, not stale context
Instead of pasting database schema into chat, the AI queries the actual schema in real time.
Building custom MCP servers
Custom MCP servers are straightforward to build using the TypeScript SDK. The pattern is always the same: create a server, define tools (functions the AI can call), connect to your API, and expose the data via stdio transport.
High-ROI custom MCP server ideas
Internal API status/health checks
Feature flag reader/toggler
Monitoring (error rates, latency, alerts)
Design system component library
Internal documentation/wiki queries
Security model
MCP servers run locally — credentials stay on your machine
Use read-only database credentials for MCP connections
Store credentials in environment variables, not in committed config files
Start with read-only servers; add write operations only with confirmation steps
Never connect to production databases without careful access restrictions
Getting started
Start with just one MCP server — GitHub is the most immediately useful. Get comfortable before adding more. Each server adds tools to the context window, so too many at once can dilute performance.

Triggers tell the AI when to apply the skill. Be specific:

The power of bad examples
Including bad examples is surprisingly effective. The AI learns what to avoid, not just what to do. The contrast between good and bad patterns makes the requirements concrete.
Keep skills focused
One concern per skill — an “accessibility skill” is better than an “everything about front-end” skill. Focused skills:
Activate more reliably
Are easier to test
Compose better with other skills
Are simpler to maintain
Testing your skills
Test by prompting WITHOUT mentioning the concern. If the accessibility skill activates automatically when you ask for a React component (without mentioning accessibility), it's working correctly.
Skill Composition
Skills are designed to be independent and composable. When multiple relevant skills exist, they all activate automatically. The key principle: separation of concerns applied to AI configuration.

Commit skill files to your repository in .claude/skills/ (or .cursor/rules/ for Cursor). Every team member's AI assistant then follows the same standards. It's like encoding your style guide, testing philosophy, and architectural patterns into a format the AI actually uses.

We've spent a few chapters building up the conductor paradigm, one AI agent deeply enhanced with skills, MCP, commands, and autonomous patterns. And it's powerful. You can build a lot with a well-configured single agent. But there's a ceiling. One agent means one context window, one sequential thread of work. And while it's building the frontend, the backend sits idle. While it's running tests, no code is being written. The orchestrator paradigm breaks through that ceiling. And here's the shift. A conductor guides one musician note by note. An orchestrator stands in front of the entire symphony and sets the direction. It then lets each musician play their part independently. In agentic development, that means instead of guiding one agent step by step, you delegate to multiple agents and review their results. Each agent has full autonomy. It can clone repos, create branches, write code, run tests, and submit pull requests. You review the pull requests, not just keystrokes. And this isn't theoretical. Let me walk you through the tools that make this real today, starting off with GitHub's Copilot coding agent. You assign it a GitHub issue, and it creates a branch, writes the code, runs tests, and opens a PR. It runs on GitHub's Actions workflow, and it's fully autonomous. We've also got Google's Jules. It clones your repo into a cloud sandbox. It works independently. You describe what you want, and it figures out implementation. There's OpenAI's Codex. It spins up a sandboxed environment for parallel tasks. Multiple agents can work on different parts of your code base simultaneously. Claude Code also has a version of this on Claude Code Web. It supports this through subagents and parallel sessions. You can spawn background agents to work on separate tasks while you continue coding. And there's Cursors background agents, too. They handle tasks in the background while you focus on something else. So what changes practically? Your workflow shifts from write prompt, review code, write prompt, review code, to define tasks, assign them to agents, and review pull requests. You're a tech lead managing a team, not a pair programmer guiding a single assistant. The interface between you and the AI shifts from conversations to pull requests. Instead of reading Claude's terminal output line by line, you're reviewing diffs, running CI, and approving merges. and the unit of work shifts from a single file or function to an entire feature or service. Orchestration makes sense when your task is decomposable into independent pieces with clear interfaces. It doesn't make sense for tightly coupled problems where every line depends on every other line. For those, the conductor paradigm is still your best bet. Here's a pro tip. Start with subagents before jumping to swarms. Subagents let you dip your toe into orchestration with a safety net. the parent agent is still doing all of that coordination. Full swarms require a little bit more upfront planning.

Multi-Agent Orchestration Patterns
The spectrum: From single agent to multi-agent teams
1. Single agent
One agent handles all tasks sequentially
Simple, no coordination overhead, but bottlenecks on complexity
2. Subagent pattern
One agent spawns child agents for specific subtasks, collects results, integrates output
Low coordination cost
3. Swarm pattern
Multiple agents work in parallel on independent chunks, share a common data structure, self-organize
Medium coordination
4. Agent Team
Agents with explicit roles (frontend engineer, DevOps, QA) collaborate via structured protocols
High coordination, but optimal for complex fullstack projects
The Sub-agent pattern: Delegation without overhead
Parent agent tasks
Write backend API schema.
Delegate to Child-1: Implement REST endpoints.
Delegate to Child-2: Write unit tests.
Merge results, verify consistency.
Benefits
Clear parent-child relationship
Easy error handling (retry single child)
Low context switching
When to use
Task breakdown is linear or tree-like
Dependencies are mostly one-way
Parent must validate/integrate results

Summary
Detailed analysis of Ralph Loops, Beads, spec-driven development, test-first AI generation, the factory model, and what's coming next
Patterns that work well
Spec-driven development
The highest-impact practice 
Teams that spec first report 2–3x better AI output
Structure specs as PRDs covering six areas: commands, testing, project structure, code style, git workflow, and boundaries
Test-first AI generation
Writing or generating tests before implementation gives the AI a target to hit

Essentially TDD with an AI partner
Project memory / rules files
CLAUDE.md, .github/copilot-instructions.md, .cursor/rules, custom instructions — encoding standards where the AI reads them automatically
Table stakes for serious AI-assisted development
The Ralph Loop
Define the goal with clear acceptance criteria, give the AI tests for self-verification, and let it iterate autonomously until all tests pass
Works excellently for well-scoped, testable tasks
Set a maximum iteration limit (5–7) to prevent runaway token usage.
The Beads Pattern
"Beads on a string" — sequential, checkpointed tasks where each step's output feeds the next
Each bead has its own acceptance criteria and commit point
Provides granular rollback that monolithic agent tasks lack
The Factory Model
The mental shift from writing code to building the factory that builds your software
Spin up multiple agents in parallel, each with different concerns
Define outcomes, review results, refine specs
Quality control parallels: precise specs are precise inputs; vague specs multiply errors across the entire fleet.
Patterns that need caution
Multi-agent orchestration
Running 3–5 agents in parallel is experimental but maturing
First-class tooling like Claude Code agent teams (with shared task lists, inbox messaging, and dependency tracking) is reducing coordination overhead
The sweet spot: independent tasks with clean boundaries
Meta-Prompting
Having AI optimize its own prompts
Mixed results — sometimes better, sometimes verbose or self-referential
Useful for brainstorming, not automation
Zero-Human-Review
Letting AI commit directly without human review
Even with tests, AI can introduce subtle issues
Always keep a human in the loop
Patterns fading
Simple ReAct: Being replaced by more sophisticated loops
Single-shot generation: Iteration is essential for quality
Rigid prompt templates: Context-aware skills and memory beat static templates
Recommendations
Write better specs (highest ROI)
Build project memory
Master the review-iterate loop
Experiment with Ralph Loops and Beads
Think in factory model terms as you scale
One new technique per month — master basics deeply

Code Review in the Age of AI
Summary
The evolving role of code review when AI writes much of the code
Includes data on AI code quality, security considerations, and the PR Contract framework
AI-augmented code review
One of the highest-value applications of AI in production workflows is code review — not replacing human review, but augmenting it
AI handles mechanical issues (bugs, security, style)
Humans focus on architecture, business logic, and design
Best practices
AI goes first, human goes second — let AI find mechanical issues
Verify every finding — AI generates false positives
Use focused review prompts — specify what you're looking for
Use a different model than the code author — different models catch different things
Keep review-specific skills — encode team review standards
Solo vs. team dynamics
Solo developers
Ship at "inference speed" — rely on extensive automated testing (>70% coverage) and AI-generated tests in real time.
Still do manual testing on the final product
Teams
AI increases code volume (PRs ~18% larger).
Incidents per PR up ~24%, change failure rate up ~30%.
Review becomes the rate limiter.
Solution: Break agent output into digestible commits and enforce incrementalism.
Security: AI's predictable weakness
Approximately 45% of AI-generated code contains security flaws:
Logic errors: 1.75x higher than human-written code
XSS vulnerabilities: 2.74x higher frequency
Rule: Code touching auth, payments, secrets, or untrusted input requires human threat model review plus a security tool pass before merge.
Review as knowledge transfer
If AI writes code nobody can explain, on-call becomes expensive
Code review is how teams share system context
When developers submit AI-generated code they don't fully understand, they break the knowledge transfer mechanism
The PR contract framework
Treat AI-generated code as a helpful draft that must be verified:
What/why: Intent in 1–2 sentences
Proof it works: Tests passed, screenshots/logs
Risk + AI role: Tier and which parts AI-generated
Review focus: 1–2 areas for human input
Core principles
Insist on proof, not promises — no PR without tests or a working demo
AI as first-pass reviewer, not final arbiter — spellcheck, not editor
Focus human review on what AI misses — security, duplication, maintainability
Enforce incremental development — never commit code you can't explain
Maintain high testing standards — ask AI to draft edge-case tests

Integrating AI agents into your CI/CD pipeline means AI actively participates in your automated workflow — reviewing code, suggesting tests, and flagging issues on every pull request.

A GitHub Action that runs AI code review on every PR
The workflow extracts the diff, sends it to Claude Code's --print mode for analysis, and posts findings as a PR comment with severity ratings.
Key components:
Trigger: PR open or synchronize events
Diff extraction: git diff between main and PR branch
AI analysis: Focused review prompt (bugs, security, test gaps)
Comment posting: Results as formatted PR comment
Integration 2: Test coverage gap filler
Identifies code with low test coverage and has AI suggest tests
Runs coverage analysis, finds files below threshold, generates test suggestions, and posts them on the PR
Integration ideas

Essential Guardrails
AI suggests, humans approve — never auto-merge or auto-deploy
Cost controls — set token budgets per run to avoid surprise bills
Fail gracefully — AI review is nice-to-have, not a pipeline blocker
Keep secrets safe — use GitHub Secrets for API keys, never hardcode
Rate limit — trigger on PR events only, not every commit
Getting started
Start with AI reviews as informational comments, not required checks. Let your team get used to the quality of AI feedback. After a few weeks, developers typically start proactively addressing AI-flagged issues before review.
The Reality of AI-Assisted Software Engineering Productivity
Summary
Data-driven analysis of how AI tools truly impact developer productivity; covers perceived vs. actual productivity, meaningful metrics, and the productivity trap
The productivity trap
There's a real productivity trap with AI tools: you feel more productive because you're generating code faster, but code quality may be lower, architecture may be degrading, and technical debt accumulates.
Research shows that perceived productivity often exceeds actual productivity. Developers report feeling 30–50% more productive, but measurable output quality sometimes drops if review discipline slips.
Vanity metrics (don't measure these)
Lines of code generated per hour
Number of AI prompts per day
Percentage of code written by AI
Speed of first draft generation
These are vanity metrics. Writing more code faster isn't the goal. Shipping better software is.
Meaningful metrics (do measure these)
1. Cycle time
How long from starting a feature to production? AI should reduce this. Track with your project management tool.
2. Bug rate
Are you shipping fewer bugs? More code faster should NOT mean more bugs. If bug rate goes up with AI, you're skipping review.
3. Test coverage trend
Is coverage going up? AI makes test generation easy, so coverage should be increasing.
4. Time-to-onboard
How quickly can new team members contribute? Good project memory and skills should accelerate onboarding.
5. Developer satisfaction
Are developers enjoying their work more? AI should reduce drudgery and free time for creative work.
6. Review turnaround
How quickly do PRs get reviewed and merged? AI-assisted reviews should speed this up.
Simple monthly check-in
Ask four questions each month:
Are we shipping features faster?
Is our bug rate the same or lower?
Is our test coverage the same or higher?
Are developers happier with their workflow?
All yes = AI integration working
Any no = investigate that area
The antidote
Keep measuring outcomes (bug rates, cycle time, production incidents) — not outputs (lines of code, commits per day). Track one surprising observation about AI-generated code each week. After three months, you'll have calibrated instincts no metric can replace.
